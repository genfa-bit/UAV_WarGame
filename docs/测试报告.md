## 战局回放（2026-10-16）

运行记录由格式版本 2 升为 3，在原有 `statistics`、`units`、`logs` 之外新增 `replay` 逐帧负载与 `map` 静态地图负载，因此任意一局已保存的对战都能以当时的画面按帧重放。逐帧数据把单位顺序冻结在首帧（队尾为红蓝基地），每单位每帧 7 个 int16（位置以 0.1 像素为单位、生命、弹药、状态与交战阶段码表下标、摧毁标志），按帧与单位交织后整体 base64；第 0 帧为部署态，帧号等于时间步。每单位每帧 14 字节，10 单位 2000 步原始约 274 KB（base64 后约 365 KB），仍小于同局的 `records` 块，[时间设置与运行记录](时间设置与运行记录说明.md#回放) 与 [回放检查记录](verification/replay-checks.json) 记录了编码、体积与取舍。

回放复用的是同一份 `snapshot()` 字典，界面层没有并行的回放视图模型，因此单位 Repeater、小地图、攻击连线画布、单位详情与统计面板都不需要回放分支。攻击连线由该帧前后 7 步的交战记录与帧位置还原，与实时快照逐字段一致，因此不需要额外持久化连线数据。统计面板中步数、累计时间、剩余/摧毁、攻击/命中/伤害、战斗力、态势与基地耐久是游标处的真值；集火目标、发现目标数、行为标签与胜负字段沿用该局最终值，这一点在文档中已注明。

回放期间不新建也不覆盖 `runs` 下的任何记录文件，该性质由逐字节比较的回归用例与源码自检第十组检查 `replay_last_run_without_touching_journals` 共同覆盖；回放中保存地图、返回部署、重新运行、载入地图与修改时间设置都会被拒绝。版本 2 的旧记录仍照常进入历史列表并可导出，只是历史行的“回放”按钮置灰并说明“旧版本记录，未包含逐帧数据，暂不支持回放”，不做迁移或回填。

底部工具栏的“载入回放…”在部署阶段也可用，刚启动程序即可回看任意旧记录；回放进行中该按钮隐藏，避免与回放条重复。进入回放时控制器会记下当时的那份部署，退出时恢复它：从运行、暂停或已结束状态进入时是本次运行前的部署，从部署阶段进入时是当时正在编辑的布局。后者是必要的——部署态的 `_run_deployment` 已被 `reset()` 清空，若沿用旧的回退逻辑，退出回放会把用户刚编辑过的单位与障碍一并退回场景初始布局。

源码自检本轮增加至十组（[回放检查记录](verification/replay-checks.json) 列出了十个检查名）；`verification/source-smoke.json` 仍是 2026-10-11 的九组证据，未在本轮重新生成。回放第 0 步的离屏截图见 [回放](verification/replay-1280x720.png)：顶部状态为“回放暂停”，右侧为战局回放侧栏，底部为回放条。尚未验证的部分只有真实鼠标拖动进度滑块的连续手感，以及无 Python 的独立 Windows 机器上的回放，离屏事件测试不能代替这两项。

## 运行记录体积（2026-10-16）

实测一局 2000 步对战（山区河谷，13,704 条记录）的体积构成：`records` 事件日志占 93.3%，`replay` 逐帧数据只占 6.6%。`records` 里 `tactical/unit_state` 一项即占全文件约七成——所以压缩帧编码的收益上限只有 6.6%，真正的体积在事件日志。据此改为归档整体压缩，取同一条路径的收益而不动回放格式。

对**同一份** payload 分别序列化量字节（不是拿两次不同对局互比）：

| 形态 | 体积 | 相对缩进明文 |
| --- | --- | --- |
| 缩进明文（原先的写法） | 8.80 MB | — |
| 紧凑分隔符 | 6.66 MB | −24% |
| 紧凑 + gzip（现在的写法） | **0.282 MB** | **−96.8%（31.3 倍）** |

压缩率来自 JSON 键名与字段名的高度重复，逐帧回放块的内容一字未改；回放在压缩落盘后仍通过进入、寻址、退出与历史可回放检查。自动保存是整文件原子重写，写盘量同步降了约 31 倍。

[map_persistence.py](../core/map_persistence.py) 的 `write_json_atomic` 增了 `compress` 参数，`read_json_document` 按 gzip 魔数自动识别。**场景另存与用户导出仍写缩进明文**——那是交付给人看的文件；同目录下明文与压缩记录可以共存，版本 2 的旧记录与手写测试文件都照常读取。压缩用 `mtime=0` 保证同样内容产出同样字节，否则回放“不新建也不覆盖记录”的逐字节比较会失去意义。

改用压缩时暴露了一个真问题：`gzip.decompress` 对截断输入抛的是 `EOFError`，而调用方只处理 `(OSError, ValueError)`。断电留下半个 gzip 流时，整个历史列表会读不出来，而不只是坏掉的那一条。现在 `read_json_document` 把 `(OSError, EOFError, zlib.error)` 统一转成 `ValueError`，与坏 JSON 走同一条跳过路径，并有回归用例在坏 JSON 之外另放一个截断归档。细节见 [记录体积检查](verification/journal-size-checks.json)。

### 二、本轮修复

1. **容量估计与填束口径不一致**：`capacity_hint` 原先按满弹量估算本波次可投入伤害，而任务束分配先扣弹药预留，导致 `required_damage` 几乎总高于实际可分配量，任务恒为 `understrength`，BDA 永远走不到"执行失败"分支。现容量估计同样扣预留，两处一致。

### 六、已知边界

1. TOT 被波次长度封顶（默认 6 步），而重规划会整体替换火力计划，因此 ETA > 6 的任务在本波次内不可能按时开火，BDA 会记为"未兑现"。再攻击标记偏高（45 局 881 次）中相当一部分属于"打不到"而非"打偏了"。
2. 迟到宽限结束后计划仍在队列中，单位抵达且目标未饱和时仍会补射；任务已被判失败，两者状态不同步。
3. 账本按 `命中率 × 伤害` 记期望值，不含暴击期望与遮挡后的二次修正，饱和判定是近似值。
4. `defended_base` 的过杀分配率 2.60% 高于 Baseline 0.52% 与 RDMA v2 0%：守卫场景目标血量下降快、计划追加密，账本饱和与任务追加之间存在一步时差。
5. SEAD 掩护判定只看直线距离（默认 220 像素），不考虑朝向、射程与视线；压制与主攻之间没有显式联动，只靠压制步数覆盖。
6. 战法切换无滞回，`ratio` 跨过 1.25 / 0.80 时立即切换。
7. 分布式降级只用指挥节点 `comm_range` 判连通，不考虑中继、丢包与延迟。
8. 任务 ID 含波次号（`{target}:{role}:{wave}`），跨波次同名目标需要自行归并。
9. 本轮未重新打包 EXE，也未做真实桌面截图。
